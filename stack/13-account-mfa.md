# Optional account TOTP

TOTP is optional for every role, including gestor. Once a verified factor exists, all application sessions must complete a TOTP challenge before protected application access. An unfinished enrollment does not require a challenge. The setup secret and QR must never be logged, transmitted to an external QR service, or retained by support. The user can cancel setup; abandoned unverified factors are removed before a new setup attempt.

Setup presents the QR/manual key and code confirmation as two steps. The copy action places the raw key on the user's clipboard only on an explicit tap; display grouping is not copied. The authenticator action hands the Auth-provided `otpauth://totp` URI to the operating system on an explicit tap, never to an HTTP service. An installed handler is not guaranteed, especially in a browser; copy and QR setup remain available, with a fallback message when launch fails. Do not use screenshots containing a real setup key as QA evidence.

## Lost authenticator: operator-only runbook

**Status: release gate open.** In a hosted disposable-account test, after admin deletion of the sole verified factor (HTTP 200, independently confirmed absent), both pre-existing AAL2 and AAL1 sessions returned HTTP 200 for Auth user lookup **and** refresh. Fresh password sign-in and re-enrollment with a different factor ID succeeded. In a separate disposable test, after factor deletion both sessions again passed lookup and refresh; an exact-user Admin password update then produced HTTP 403 for both Auth user lookups and HTTP 400 for both refreshes. The old password was rejected and the new password accepted. Both fixtures were deleted and independently confirmed absent (HTTP 404). These are observations on sampled sessions, not proof of universal invalidation. Validate the complete operator procedure, containment, secure handoff, ordering and failures with approval on isolated staging before release; record sanitized results. Never perform a production test or delete a real factor without case-specific authorization. This procedure concerns an EducaDor Auth user, not recovery of an operator's Supabase Dashboard account.

The user should sign out and contact the platform operator. Password reset alone does not remove MFA. There is no application-side lost-factor recovery, bypass, SMS fallback or recovery-code flow. Normal authenticated factor management in account security is not an operator recovery path. TOTP remains optional for every role.

### Prerequisites and approval

- Open a restricted case. An authorized verifier must complete the organisation's **approved offline identity-verification process**, independently of the request channel, and bind its result to the actual account owner. Email, support chat, possession of an email account, or a requester-provided user ID alone is not identity proof. If the process, verifier or required evidence is unavailable, stop and escalate; do not invent a substitute.
- Obtain case-specific approval from the designated authority under that process. The executor must be an explicitly authorized operator, ideally distinct from the verifier/approver. Confirm the approved environment and project reference before accessing Auth. If there is suspected account takeover, stop recovery and follow the organisation's incident procedure, including appropriate containment; removal of MFA reduces protection.
- Use an individually accountable Dashboard operator with only the project access needed for this task, on a trusted workstation. Verify the selected project in the Supabase Dashboard. If administrative SDK access is necessary, use an approved trusted server-side environment and a project-specific secret/service-role credential accessed only for the case. Such credentials have broad privileges and bypass RLS; they are **not** factor-scoped. Never put them in the app, browser code, shared shell history, tickets or logs. Do not grant broad access merely for convenience; remove temporary access afterwards.

### Identify, remove, verify

1. Resolve the verified person to exactly one Supabase Auth user in the approved project's Dashboard Auth user management; compare the Auth user UUID and account details against authoritative organisational records and the case. A name or email match alone is insufficient. Recheck project reference and UUID before any mutation. If identity or account mapping is ambiguous, stop.
2. Inspect that user's factors via the Dashboard if it exposes the required details and deletion control, or via the server-side [Supabase JavaScript Admin MFA API](https://supabase.com/docs/reference/javascript/auth-admin-listfactors): `supabase.auth.admin.mfa.listFactors({ userId })`. The [SDK implementation](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueAdminApi.ts) requires `userId`; the published list example omits it. Check the error and inspect `data.factors`. Identify the affected TOTP factor by its exact ID, type, status and available distinguishing metadata, matched to the approved case. If multiple factors cannot be distinguished, stop; do not delete all factors as a shortcut. Preserve unrelated factors.
3. Obtain separate case-specific approval for **disruptive password replacement** and session containment, including the impact on all devices and any non-password sign-in methods. This is not a pure logout. The documented server-only [Admin updateUserById](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid) accepts `supabase.auth.admin.updateUserById(userId, { password: newPassword })`; it changes the password directly without a confirmation flow and requires a trusted server-side project secret/service-role credential. Do not collect a user's JWT: [Admin signOut](https://supabase.com/docs/reference/javascript/auth-admin-signout) requires one and is not this procedure. Never invent a UUID-only sign-out endpoint or modify Auth tables directly.
4. Before mutation establish an approved, effective target-specific containment and coordination plan that prevents new sign-ins and use of existing sessions during the entire operation, including the deletion-to-password-update interval, without disabling MFA enforcement. Do not assume a Dashboard control or password change alone achieves this. Coordinate with the user not to sign in until released; that instruction alone does not contain an attacker. Prepare a high-entropy unique temporary password and an approved confidential handoff to the independently verified owner; never expose it in commands, shell history, logs, tickets, raw responses or insecure messages. If containment, secure generation/handoff, authorization, or the trusted execution environment is unavailable, **stop before deletion and escalate**. Do not release containment on an uncertain outcome. This workflow and containment still require end-to-end staging validation.
5. While containment is in effect, immediately recheck project, user UUID and exact factor ID against approval and current list. Use the Dashboard factor deletion control only if it clearly identifies that factor, or documented [Admin deleteFactor](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor) with `supabase.auth.admin.mfa.deleteFactor({ userId, id: factorId })`. Check the error. Never delete the user, alter Auth tables directly, or disable MFA enforcement. **Deletion does not reliably sign out sessions.** Removing the last verified factor can allow existing AAL1 sessions through the MFA gate, while AAL2 sessions may remain active; the interval before password replacement is a security risk even if short.
6. Without releasing containment or allowing a new sign-in, perform the separately authorized exact-user Admin password update as soon as possible; check the returned error. Independently re-list factors and confirm the exact deleted ID is absent and unrelated factors remain. If another verified factor remains, the user still needs its challenge; do not remove it without separate identification and approval. The test used deletion followed by password update, not the reverse; do not assume reversing the sequence eliminates races. A successful update or sampled tests cannot prove all sessions were revoked or exclude concurrent sessions. In an approved disposable staging test, independently check old AAL1 and AAL2 Auth lookup and refresh, old/new password behavior, and failure/uncertain outcomes; never test live user credentials or retain tokens.
7. Maintain containment and escalate any uncertainty before handing the temporary password to the verified owner using the approved confidential channel; never put it in ordinary support chat, email, tickets or logs. Only release containment under the approved plan after the update and factor verification succeed and residual-token risk has been addressed. Have the user sign in and promptly replace the temporary password privately with their own; support must not collect it. If no verified factor remains, explain that the account is no longer MFA-protected and encourage voluntary re-enrollment via **Perfil → Segurança e MFA**. The user alone scans the QR or copies the key and enters the code; support must not see or collect either. If they choose to re-enroll, verify with the user that setup completes, then check via the admin factor list that a new TOTP factor is `verified` and has a different ID. Have the user sign out, sign in and complete the new challenge. If they decline, record that re-enrollment was offered and declined, not completed. Never require enrollment as a condition of this recovery.

Even after the password update, previously issued access JWTs may be independently verifiable until expiry; Auth lookup/refresh failures do not prove every application endpoint rejects them. In particular, app context checks use the caller JWT's `session_id` and must not be assumed to check that the Auth session still exists. The service-role credential bypasses RLS and is not the caller's JWT. Previously issued presigned URLs may remain usable until expiry, and public objects remain public. Account for these residual exposures in the containment plan; do not claim immediate universal invalidation.

### Failures, evidence and closure

- If identity, authorization, project, account or factor is uncertain, access is denied, or a list fails before mutation: make no deletion; record and escalate. If deletion errors, times out, or its response is uncertain, maintain containment and **do not blindly retry**. Treat deletion as potentially completed; escalate immediately and carry out the pre-approved password-replacement containment response if safe and authorized, then re-list the exact user's factors. If the ID remains, investigate and obtain approval before retry; if absent, verify remaining factors. If listing is unavailable, leave the case pending and escalate.
- If the password update fails, times out, or its outcome is uncertain, maintain containment, do not hand off a possibly invalid password or blindly retry, and escalate immediately to the security owner. If deletion may have occurred but the update or verification cannot be completed, do not claim the account is secure or close the case. Record password-update approval, attempt, result and uncertainty separately from factor deletion, without secrets. An unexpected successful refresh or unavailable test requires investigation; rejection of sampled refreshes is not proof of universal revocation.
- If the wrong factor was removed, an unrelated factor changed, compromise is suspected, or the user reports an unexpected notification: stop, initiate the incident procedure and notify the designated security owner. Never attempt to restore a deleted secret. If sign-in, re-enrollment, verification or a subsequent challenge fails, leave the case open and escalate; do not bypass the challenge. Record partial outcomes, including when a remaining factor prevents access.
- Keep a minimally detailed, access-controlled case/audit record according to organisational retention policy: case reference, environment/project reference, user UUID, affected factor ID/type/status, verification method and outcome (not identity-document copies), approvals, operator and timestamps, actions and sanitized error category, before/after verification, user notification, re-enrollment offered and outcome, and incident/escalation references. Record who verified each step. Never record passwords, TOTP codes, setup keys, QR codes, `otpauth` URIs, recovery links, tokens, service keys, raw responses or screenshots containing secrets. Close only after recording the final or explicitly pending outcome and removing temporary operator access.

The shared Edge caller checks the current server-side factor state using the caller JWT before invoking service-role actions. Existing presigned URLs remain usable until their expiry, and the public bucket is public. Auth's own session/factor endpoints remain available for challenge, unenrollment, sign-out and password recovery. Future SECURITY DEFINER RPCs and Edge service-role flows must enforce `public.require_mfa_if_enrolled()` using the authenticated caller, not the service-role JWT. New direct-table policies must also enforce MFA. Recheck these boundaries on integration of push and notification preferences.
