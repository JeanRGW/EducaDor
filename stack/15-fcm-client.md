# FCM client (work in progress)

The client is gated off without explicit public `FIREBASE_API_KEY`, `FIREBASE_APP_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_PROJECT_ID`, and, for web, `VAPID_PUBLIC_KEY` Dart defines. These are public Firebase application configuration, not service-account credentials. Use the correct Firebase app ID/API key per platform. No credentials are included in this repository. iOS and desktop are unsupported. A real Firebase project, VAPID key, Android application registration, browser/device permission and FCM server configuration are operator prerequisites; do not deploy or configure these without approval.

The web SDK uses the custom worker path supported by FlutterFire 17; the worker lives under `/push/` so it does not replace the shell worker. Its URL carries only public Firebase app configuration. It has no fetch handler and renders generic content, ignoring payload-provided URLs. Verify CSP, worker registration, foreground and background behavior on real browsers and installed PWAs before launch. Android uses explicit FirebaseOptions rather than a checked-in google-services.json; verify build and background behavior on a real Android device. Permission is requested only from the settings control.

The backend must implement the agreed token/preference RPCs and exclusive token ownership. A best-effort logout cleanup cannot guarantee deletion after an expired session or network failure. Shared-device behavior and stale async registration need real-device and adversarial tests before enabling push. This implementation is not release-ready until these gates and tests pass.

Known blockers: controller currently needs fake-transport tests for denial, refresh, opt-out and concurrent account changes; registration/cleanup races have not been proven safe. Web FlutterFire's `onTokenRefresh` is a no-op, so refresh occurs on reinitialization/getToken rather than via that stream. Dashboard bell actions still display unavailable. The MFA security route is supplied by a separate change. Do not merge or enable this work until these are resolved. Firebase options are checked only for presence, not semantic validity. The Android native build and browser/PWA integration have not been tested.

Local evidence: `flutter analyze` passed, 274 Flutter tests passed, 10 Node PWA tests passed, and release web build plus shell worker generation succeeded with staging's existing public configuration and no Firebase credentials. None exercise real FCM.

Certificate notifications require an authoritative new-issuance signal: `issue-certificate` returns an ID for both newly created and existing certificates. No certificate push is sent until that contract is extended to distinguish creation, avoiding repeated notifications on historical reads.
