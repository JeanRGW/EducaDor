# Backup and recovery: offline prototype, activation blocked

**The publication workflow is hard-disabled and is not production-ready.** It declares a daily 03:17 UTC schedule and manual dispatch, but the job cannot run until its hard-disable is deliberately removed after review. No provider or credentials were accessed during validation. Archives use signed version 2 manifests and bounded streams. Independent review is mandatory before activation. The HMAC authenticates a version 3 marker, not proof of final readback and inventory.

**Stateless retention is opt-in and rests on operator attestations, not a technical lock.** Authenticated v3 timestamps select the newest run per UTC day for the most recent 7 distinct days and per ISO week for the most recent 4 distinct weeks. The union, the new run and the newest previous run are retained. Defaults are configurable by `BACKUP_DAILY_RETENTION` and `BACKUP_WEEKLY_RETENTION`; monthly retention is not implemented. V2, malformed, tampered, ambiguous, duplicate or non-monotonic timestamps and unknown objects block pruning. Wholesale rollback and clock manipulation remain undetectable without an external high-water mark.

## Activation blockers

Before activating the daily workflow, the operator and security reviewer must approve all of the following:

1. Approve a B2 storage budget and reservation strategy. Backblaze B2 offers 10 GB free storage and free egress up to three times average stored data; recheck current provider terms and quotas. Set total budget at most 9,000,000,000 bytes, reserve space for other usage and incomplete uploads, and monitor actual usage and egress. Never delete before a verified replacement. No paid fallback is approved.
2. DB dump scope, consistency and hosted restore strategy: Supabase-managed Auth, Storage metadata, extensions, roles, migration history and provider-managed schemas require separate review. A generic `pg_dump` is not evidence that hosted Supabase is recoverable. Test the precise approved dump and restore procedure against a disposable Supabase project before relying on it.
3. Scoped server-side Storage and database credentials, their ownership, rotation and incident response; demonstrate that the selected API supports bounded listing, upload, read-back and deletion without exposing credentials. Supabase S3 credentials may be broad: review effective permissions rather than assuming bucket scoping. Never put them in app code or PR jobs. Select an operator-approved key custodian and offline recovery process.
4. Independently review the publisher and signed archive integration. No out-of-band high-water mark exists; wholesale rollback and clock manipulation are undetectable. V2 markers are rejected. GitHub concurrency cannot lock out external writers. Unknown or incomplete objects block publication; inventory comparison does not detect same-size overwrites or changes between checks. Enforce exclusive access independently.
5. A protected GitHub environment with branch restriction to protected main and an explicitly approved reviewer policy; confirm the repository plan actually enforces those settings before storing secrets. A YAML environment name alone is not protection. Scheduling and any first backup require separate explicit authorization. Review the operational tradeoff below before changing reviewer protection.

Until these decisions and independent review are complete, **do not enable the workflow, upload a production dump, or prune the bucket**. The selected destination is private Backblaze B2 bucket `educador-backups`, endpoint `https://s3.us-east-005.backblazeb2.com`, S3 path-style. This backs up database dumps only: uploaded covers, avatars, PDFs, audio, GIFs and image sequences are separate object bytes, not backed up or recoverable by this workflow. YouTube videos remain on YouTube. A database backup alone is not complete disaster recovery.

6. Verify the B2 bucket's versioning and lifecycle configuration before activation. Configure lifecycle rules to expire noncurrent versions and abort incomplete multipart uploads, or disable versioning if B2 permits it for this bucket. B2 lifecycle configuration may require the B2 native API or UI rather than S3. `ListObjectsV2` cannot see noncurrent or hidden versions; `delete-object` may leave hidden versions consuming storage. Reconcile the listing-based budget and reserve against **all** retained versions, delete markers and incomplete uploads using independently verified provider accounting. Lifecycle timing and retained bytes still require monitoring; this gap is not solved by the publisher.

## Publisher configuration and limitations

The disabled workflow uses the `backup-production` environment; initially configure required reviewers, prevent self-approval where supported, restrict deployment to protected `main`, and verify actual plan enforcement. Once authorized and enabled, each scheduled run waits for manual reviewer approval, requiring up to one approval per day. For truly unattended daily backups, the operator must either (a) explicitly approve removing per-run reviewer approval while retaining the protected branch restriction and environment-scoped secrets, or (b) run the same script on an always-on operator machine with credentials securely stored there and appropriate independent controls. Removing reviewers weakens a security gate and requires a deliberate risk decision, not an automatic change. GitHub concurrency may replace pending runs; monitor failures and missed runs. Weekly retention is derived from the daily runs; no separate weekly backup job is needed. `BACKUP_ENABLED` must be the repository variable `true`, and manual runs also require the confirmation input. Store the three attestation variables in the protected environment rather than at repository level (the workflow reads `vars` in environment scope first) so changing them follows the same review gate; a repository-level value would bypass environment protection. Removing the hard-disable requires a reviewed code change after all blockers are resolved.

Environment variables: `BACKUP_S3_ENDPOINT` is an HTTPS B2 S3 endpoint such as the one above. Other B2 regions are accepted only in the form `https://s3.REGION.backblazeb2.com` (optional trailing slash); set `AWS_DEFAULT_REGION` to the exact matching region, e.g. `us-east-005`, for B2 request signing. Mismatched regions are rejected before network access; `BACKUP_TOTAL_BUDGET_BYTES` is an operator-approved allocation no greater than 9,000,000,000 bytes. `BACKUP_NON_BACKUP_RESERVE_BYTES` must cover all other project storage, growth and **all incomplete multipart uploads**, including uploads outside this bucket. `ListObjectsV2` does not include multipart parts. This code does not inventory multipart uploads and cannot automatically establish headroom; a conservative independently verified reserve and prohibition of other multipart writers are mandatory. `BACKUP_EXCLUSIVE_WRITER_ATTESTED`, `BACKUP_MULTIPART_RESERVE_ATTESTED` and `BACKUP_NO_ROLLBACK_CLOCK_ATTESTED` must all be `true`, but are operator assertions, not technical locks or proof. Starting a run with the third false still refuses to publish, so no deletion occurs. Unknown/incomplete listed objects fail closed. Ensure the bucket exists, is private, and accepts `application/octet-stream` objects up to 40,000,000 bytes. Monitor actual usage and update the reserve; concurrent growth beyond it invalidates the estimate.

Publication fully verifies the new archive on readback and the newest previous archive, authenticates marker, signed manifest and inventory for all runs, and reauthenticates each deletion candidate before deletion without downloading its body. Other retained bodies are not re-read on each publication; corruption is detected by periodic full audit, not necessarily before an unrelated deletion. The conservative pre-network estimate covers new bytes, up to one maximum previous archive, twice maximum metadata for 32 runs and 20 MB protocol allowance. Audit first lists inventory, then requires a budget covering all listed bytes plus 20 MB before downloads. Allow for monthly aggregate traffic and audit frequency; neither estimate is a provider-enforced network cap. Unbounded list pages, errors or unexpected SDK behavior may exceed it. The marker does not prove historical final readback or hosted restorability.

After approval, run a full audit weekly or monthly in a secure operator environment with the same isolated AWS CLI configuration, HMAC key and independently trusted public signing key: `python3 scripts/backup/publish.py audit`. `BACKUP_EGRESS_BUDGET_BYTES` must be explicitly set. The bare argument `audit` is reserved for this command; publish a directory named audit using `./audit` or an absolute path instead. This checks every retained run's marker, signature, inventory and all ciphertext bytes, and checks inventory again. No audit job or schedule is enabled. Investigate any failure and preserve all evidence.

Publication is split into isolated phases so no single compromised dependency sees every secret: the dump step receives only `BACKUP_DATABASE_URL`; the encryption/signing step receives only the signing private key (plus the public key) and uses a dedicated GNUPGHOME whose agent is killed and directory removed; the publisher step receives only the HMAC key and S3 credentials, imports only the public key into a separate verification GNUPGHOME, and runs the AWS CLI with an explicit environment allowlist that excludes the database URL, HMAC key and signing material. `pg_dump`, GPG and the AWS CLI are each invoked with minimal environments. The pinned awscli 1.36.40 cannot build its argument parsers on Python 3.14 ("badly formed help string"), so the loopback CLI test runs under Python 3.12; the test is hermetic (isolated config/credentials, `AWS_EC2_METADATA_DISABLED`, path-style addressing, hostile proxy/profile/session variables removed, explicit readiness wait) and rejects unsupported interpreters with an actionable message.

Set `BACKUP_RECIPIENT_FINGERPRINT` and `BACKUP_PUBLIC_KEY` as environment variables after independent fingerprint verification. Store `BACKUP_DATABASE_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, and a randomly generated at least 32-byte hex `BACKUP_HMAC_KEY_HEX` as environment secrets. The HMAC key must remain stable and be backed up securely: rotation makes old runs unrecognized and blocks publication. It authenticates completion metadata only, not the archive's restore source. Never put the private decryption key in CI. The database URL and S3 credentials may have broad privileges; approve and limit them independently. The workflow pins AWS CLI 1.36.40, isolates its config with path-style addressing and disables retries; dependencies are not hash-pinned and require supply-chain review. A loopback S3 protocol fixture exercises the actual CLI paths, pagination and failure handling (`BACKUP_CLI_TEST=1` with that version installed); this does not prove B2 compatibility. Hosted Supabase currently runs PostgreSQL 17.6; the workflow installs the PGDG PostgreSQL 17 client and verifies the `pg_dump` major version before dumping. Recheck the hosted version and client compatibility before activation. Experimental retrieval downloads and checks every part, HMAC and independently trusted signing fingerprint before producing a local archive: `python3 scripts/backup/publish.py retrieve RUN_ID /secure/scratch/retrieved`; then use `archive.py unpack` as below. Retrieval cannot establish freshness or prove that final publication checks completed. No hosted restore is provided.

### Protected environment setup

After review, configure the GitHub `backup-production` environment with protected-main restrictions and required reviewers; verify enforcement. Create a bucket-scoped B2 application key with only the list/read/write/delete capabilities needed for `educador-backups`. Never put its values in the repository, logs or PR. Set environment secrets `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_DATABASE_URL`, `BACKUP_HMAC_KEY_HEX`, and `BACKUP_SIGNING_PRIVATE_KEY`. Store the stable HMAC key and offline decryption key in independently secured recovery custody.

Set protected environment variables `BACKUP_S3_ENDPOINT`, `AWS_DEFAULT_REGION` (matching the endpoint), `BACKUP_TOTAL_BUDGET_BYTES` (at most 9,000,000,000), `BACKUP_NON_BACKUP_RESERVE_BYTES`, `BACKUP_EGRESS_BUDGET_BYTES`, `BACKUP_RECIPIENT_FINGERPRINT`, `BACKUP_PUBLIC_KEY`, `BACKUP_SIGNER_FINGERPRINT`, `BACKUP_EXCLUSIVE_WRITER_ATTESTED`, `BACKUP_MULTIPART_RESERVE_ATTESTED`, and `BACKUP_NO_ROLLBACK_CLOCK_ATTESTED`. Verify fingerprints out of band. The three attestations must only be set true after independently verifying the corresponding conditions. Retention defaults to 7 and 4; optional environment variables `BACKUP_DAILY_RETENTION` and `BACKUP_WEEKLY_RETENTION` override them. `BACKUP_ENABLED` must also be true for a future authorized run. A separate reviewed code change removing `false &&`, a verified restore exercise, cost review, and explicit authorization are required before any run or scheduling.

### Manual recovery runbook

There is no automated restore of a hosted instance. When an operator must recover:

1. Freeze writes: disable the workflow (keep the hard-disable), stop every other bucket writer, and capture a fresh inventory of keys/sizes before touching anything. Record the inventory and current time in the incident log.
2. Preserve evidence: copy the signing public key, HMAC key and the exact candidate run IDs to a protected location; never paste keys or tokens into logs or issues. Keep all candidate objects until recovery succeeds.
3. Authenticate each candidate offline with `publish.retrieve RUN_ID /secure/scratch/retrieved`. This verifies the marker HMAC, signed v3 run ID/creation time, manifest signature against the independently trusted fingerprint, exact inventory and every ciphertext byte before writing one output directory. Treat failure as data loss for that candidate, not as a reason to skip verification.
4. Run `archive.py unpack` on the retrieved directory with the trusted signing fingerprint and the offline private decryption key. For a protected key, set `BACKUP_GPG_PASSPHRASE_FILE` to a regular, current-user-owned mode-0600 file containing its passphrase (no symlinks in the path); keep it on secure scratch and remove it after use. Never put the passphrase in an argument or log. Then inspect the SQL dump on a disposable host. Confirm the dump reflects the intended restore point; the marker time is creator-asserted, not a provider timestamp.
5. Restore only into an independently reviewed, disposable target (the Docker fixture tests a generic PostgreSQL database, not Supabase-managed Auth/Storage/extensions/roles). Compare row counts and key tables against evidence before any production step. Applying to production requires a separate approved plan with explicit operator authorization.
6. Only after a verified replacement is safely stored may an authorized operator remove obsolete runs. Use a reviewed exact-key list; never wildcard or delete objects whose ownership, completeness or authenticity is unknown. If any step disagreed with the recorded inventory, stop and escalate rather than pruning.

### Ambiguous runs and manual cleanup

Never assume a marker proves a completed run. Stop all writers and preserve the bucket; capture inventory and retain the signing and HMAC keys. An authorized operator must independently retrieve and verify candidate archives, assess freshness from trusted external evidence, and preserve adequate separately verified copies before considering any cleanup. Inventory unknown objects and incomplete multipart uploads separately; do not delete unowned data or assume these listings are complete. Manual deletion requires a reviewed, explicitly authorized per-object plan and independent verification of the exact targets. There is no validated general deletion procedure and no automated cleanup outside the attested stateless prune; if evidence or ownership is uncertain, stop and escalate. Stateless retention cannot detect a wholesale rollback to an older authentic state; that residual risk is accepted only by the explicit no-rollback attestation.

## Offline archive format and verification

For experiments only, generate an encryption-capable GPG key on a trusted machine; keep the private key offline, encrypted and backed up in a separately secured location with a tested recovery custodian. Export only the verified public key to the packaging environment. Verify its full fingerprint out of band. Losing the private key makes the archive unrecoverable. Never upload private keys, dumps, passwords or GPG home directories as CI artifacts, logs or repository files. The prototype does not generate database dumps and does not protect plaintext on disk: use an encrypted private scratch directory, `umask 077`, sufficient space and independently managed cleanup. Secure deletion on SSDs or hosted runners cannot be assumed.

```bash
umask 077
python3 scripts/backup/archive.py pack /secure/scratch/dump.sql /secure/scratch/archive --recipient ENCRYPTION_FINGERPRINT --signer SIGNING_FINGERPRINT
BACKUP_GPG_PASSPHRASE_FILE=/secure/scratch/passphrase python3 scripts/backup/archive.py unpack /secure/scratch/archive /secure/scratch/verified.sql --signer SIGNING_FINGERPRINT
```

This prototype requires Linux with `/proc` and `renameat2`. Encryption ignores GPG configuration and disables configured extra recipients; the specified encryption fingerprint is the only intended recipient. Version 2 signs the exact manifest with a separate signing key and verifies it against the independently trusted full primary signing fingerprint before reading ciphertext or decrypting. Version 1 unsigned archives are rejected. A signature authenticates the signer, not freshness: replay and compromised signing keys remain risks. Limits are enforced on actual source, compressed, ciphertext and decompressed bytes (600 MB each); parts are at most 40 MB. Linux directory descriptors, no-follow opens and atomic no-replace publication prevent pathname substitution and overwrite. Parent directories must exist and be trusted against untrusted writers. Scratch directories are private, but crashes or SIGKILL can leave plaintext behind: use encrypted scratch and arrange operator cleanup; secure deletion is not guaranteed.

Generate a distinct signing key. Protect its private key and passphrase in a reviewed, restricted CI environment with approved access and rotation, never PR jobs; use an agent or protected file descriptor for passphrases, never command-line arguments or logs. The packer only needs the encryption public key, while the restore environment holds the encryption private key and independently verified signing public key. `BACKUP_PUBLIC_KEY` must contain the encryption public key (and the independently verified signing public key for publisher verification), never the encryption private key. `BACKUP_SIGNING_PRIVATE_KEY` is the separate unprotected signing private key, stored as a protected environment secret; the workflow does not supply a signing passphrase. Pin `BACKUP_SIGNER_FINGERPRINT` independently and review the risks of an unprotected CI signing key before activation. This integration is not approved for production.

## Disposable restore verification

```bash
BACKUP_DOCKER_TEST=1 python3 -m unittest discover -s scripts/backup -v
```

This creates a fresh Docker `postgres:16` container without network access or published ports, creates a fixture database, dumps it, packages and unpacks it, restores into a second fresh database in that container, verifies a row and removes the container. It cannot restore to a supplied URL or live database. Docker image availability and daemon access are required. This tests only a generic PostgreSQL fixture, not hosted Supabase, Auth, permissions, extensions or Storage. No live restore command is provided: recovering a hosted instance requires a separately reviewed plan and explicit operator approval. Do not point generic SQL restore at production.
