# Backup and recovery: enabled workflow with remaining operator gates

**The publication workflow is enabled and activation is approved.** It declares a daily 03:17 UTC schedule and manual dispatch, and each run requires `BACKUP_ENABLED == 'true'` on protected `main`; manual runs also require the `confirm` input. Hosted restore validation, B2 lifecycle/versioning and key custody remain operator responsibilities. Archives use signed version 2 manifests and bounded streams. The HMAC authenticates a version 3 marker, not proof of final readback and inventory.

**Stateless retention is opt-in and rests on operator attestations, not a technical lock.** Authenticated v3 timestamps select the newest run per UTC day for the most recent 7 distinct days and per ISO week for the most recent 4 distinct weeks. The union, the new run and the newest previous run are retained. Defaults are configurable by `BACKUP_DAILY_RETENTION` and `BACKUP_WEEKLY_RETENTION`; monthly retention is not implemented. V2, malformed, tampered, ambiguous, duplicate or non-monotonic timestamps and unknown objects block pruning. Wholesale rollback and clock manipulation remain undetectable without an external high-water mark.

## Remaining operator gates

Activation is approved. The following operator responsibilities remain; maintain and revalidate them before relying on backups for recovery:

1. Approve a B2 storage budget and reservation strategy. Backblaze B2 offers 10 GB free storage and free egress up to three times average stored data; recheck current provider terms and quotas. Set total budget at most 9,000,000,000 bytes, reserve space for other usage and incomplete uploads, and monitor actual usage and egress. Never delete before a verified replacement. No paid fallback is approved.
2. Hosted restore validation: the workflow emits a data-only `pg_dump` of `public` and `auth` (excluding the provider-managed `auth.schema_migrations` bookkeeping table) instead of a full schema dump. The local drill proves this dump restores into a freshly migrated local Supabase project, including `auth.users` rows needed by `public.profiles` foreign keys. A disposable hosted Supabase project still requires validation with matching Auth/Postgres versions; local success is not proof that hosted Auth internals, roles or Storage metadata restore correctly. Hosted restoration is not validated and must not be claimed. Object bytes remain outside this contract.
3. Scoped server-side Storage and database credentials, their ownership, rotation and incident response; demonstrate that the selected API supports bounded listing, upload, read-back and deletion without exposing credentials. Supabase S3 credentials may be broad: review effective permissions rather than assuming bucket scoping. Never put them in app code or PR jobs. Select an operator-approved key custodian and offline recovery process.
4. Independently review the publisher and signed archive integration. No out-of-band high-water mark exists; wholesale rollback and clock manipulation are undetectable. V2 markers are rejected. GitHub concurrency cannot lock out external writers. Unknown or incomplete objects block publication; inventory comparison does not detect same-size overwrites or changes between checks. Enforce exclusive access independently.
5. A protected GitHub environment with branch restriction to protected main and an explicitly approved reviewer policy; confirm the repository plan actually enforces those settings before storing secrets. A YAML environment name alone is not protection. The operator approved unattended daily runs, so per-run reviewer approval may be omitted; retain the protected branch restriction and environment-scoped secrets, and review the operational tradeoff below when changing reviewer protection.

The destination is private Backblaze B2 bucket `educador-backups`, endpoint `https://s3.us-east-005.backblazeb2.com`, S3 path-style. A run still requires `BACKUP_ENABLED == 'true'` (and `confirm` for manual dispatch); disabling either stops new runs without deleting existing archives. **Never upload an unverified dump or prune the bucket without a verified replacement.** This backs up data-only dumps of the `public` and `auth` schemas: uploaded covers, avatars, PDFs, audio, GIFs and image sequences are separate object bytes, not backed up or recoverable by this workflow. YouTube videos remain on YouTube. A database backup alone is not complete disaster recovery.

6. Verify the B2 bucket's versioning and lifecycle configuration and keep it verified. Configure lifecycle rules to expire noncurrent versions and abort incomplete multipart uploads, or disable versioning if B2 permits it for this bucket. B2 lifecycle configuration may require the B2 native API or UI rather than S3. `ListObjectsV2` cannot see noncurrent or hidden versions; `delete-object` may leave hidden versions consuming storage. Reconcile the listing-based budget and reserve against **all** retained versions, delete markers and incomplete uploads using independently verified provider accounting. Lifecycle timing and retained bytes still require monitoring; this gap is not solved by the publisher.

## Publisher configuration and limitations

The workflow uses the `backup-production` environment; configure protection per operator policy, restrict deployment to protected `main`, and verify actual plan enforcement. Per-run reviewer approval is optional and the operator chose unattended daily runs; if it is enabled, each scheduled run waits for approval. For unattended backups the operator must either (a) explicitly approve omitting per-run reviewer approval while retaining the protected branch restriction and environment-scoped secrets, or (b) run the same script on an always-on operator machine with credentials securely stored there and appropriate independent controls. Removing reviewers weakens a security gate and requires a deliberate risk decision, not an automatic change. GitHub concurrency may replace pending runs; monitor failures and missed runs. Weekly retention is derived from the daily runs; no separate weekly backup job is needed. `BACKUP_ENABLED` must be the environment variable `true`, and manual runs also require the confirmation input. Store the three attestation variables in the protected environment rather than at repository level (the workflow reads `vars` in environment scope first) so changing them follows the same review gate; a repository-level value would bypass environment protection. To pause backups, set `BACKUP_ENABLED` to `false` or disable the workflow; this never deletes existing archives.

Environment variables: `BACKUP_S3_ENDPOINT` is an HTTPS B2 S3 endpoint such as the one above. Other B2 regions are accepted only in the form `https://s3.REGION.backblazeb2.com` (optional trailing slash); set `AWS_DEFAULT_REGION` to the exact matching region, e.g. `us-east-005`, for B2 request signing. Mismatched regions are rejected before network access; `BACKUP_TOTAL_BUDGET_BYTES` is an operator-approved allocation no greater than 9,000,000,000 bytes. `BACKUP_NON_BACKUP_RESERVE_BYTES` must cover all other project storage, growth and **all incomplete multipart uploads**, including uploads outside this bucket. `ListObjectsV2` does not include multipart parts. This code does not inventory multipart uploads and cannot automatically establish headroom; a conservative independently verified reserve and prohibition of other multipart writers are mandatory. `BACKUP_EXCLUSIVE_WRITER_ATTESTED`, `BACKUP_MULTIPART_RESERVE_ATTESTED` and `BACKUP_NO_ROLLBACK_CLOCK_ATTESTED` must all be `true`, but are operator assertions, not technical locks or proof. Starting a run with the third false still refuses to publish, so no deletion occurs. Unknown/incomplete listed objects fail closed. Ensure the bucket exists, is private, and accepts `application/octet-stream` objects up to 40,000,000 bytes. Monitor actual usage and update the reserve; concurrent growth beyond it invalidates the estimate.

### Database connection URL

`BACKUP_DATABASE_URL` must be a full libpq URI. The accepted session-pooler form is:

```text
postgresql://postgres.<project-ref>:<DB_PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require
```

`postgres://` is accepted as an equivalent scheme. The URI must include user information (`@`), a non-empty host and a database name in the path; the port is optional and defaults to 5432. `?sslmode=require` is required by the Supabase pooler: when `sslmode` is absent the dump step prints a warning but does not fail, because a direct connection may supply TLS settings otherwise. A bare database name or malformed URI fails immediately with an actionable message.

Percent-encode reserved characters in the username and password using RFC 3986 rules: `@`, `:`, `/`, `?`, `#`, `[`, `]`, `&`, `=` and literal `%` must be written as `%40`, `%3A`, `%2F`, `%3F`, `%23`, `%5B`, `%5D`, `%26`, `%3D` and `%25`. Encoding `@` is mandatory when the password contains it; an unencoded `@` makes the host unparseable. Copy the session-pooler URI from the Supabase dashboard where possible and only substitute the database password.

Before invoking `pg_dump`, the workflow runs `python3 scripts/backup/check_db_url.py`, which reads `PGDATABASE`, parses the URI with `urllib.parse` and prints only the scheme plus whether host, port, user, path (database) and `sslmode` are present; it never prints the URL, user, host, password or query values. The dump then passes the value explicitly as `"$PG_DUMP" --dbname "$PGDATABASE"`: libpq does not expand a `postgresql://` URI supplied only through the `PGDATABASE` environment variable, so omitting `--dbname` makes `pg_dump` treat the value as a database name and connect to a local Unix socket.

Publication fully verifies the new archive on readback and the newest previous archive, authenticates marker, signed manifest and inventory for all runs, and reauthenticates each deletion candidate before deletion without downloading its body. Other retained bodies are not re-read on each publication; corruption is detected by periodic full audit, not necessarily before an unrelated deletion. The conservative pre-network estimate covers new bytes, up to one maximum previous archive, twice maximum metadata for 32 runs and 20 MB protocol allowance. Audit first lists inventory, then requires a budget covering all listed bytes plus 20 MB before downloads. Allow for monthly aggregate traffic and audit frequency; neither estimate is a provider-enforced network cap. Unbounded list pages, errors or unexpected SDK behavior may exceed it. The marker does not prove historical final readback or hosted restorability.

After approval, run a full audit weekly or monthly in a secure operator environment with the same isolated AWS CLI configuration, HMAC key and independently trusted public signing key: `python3 scripts/backup/publish.py audit`. `BACKUP_EGRESS_BUDGET_BYTES` must be explicitly set. The bare argument `audit` is reserved for this command; publish a directory named audit using `./audit` or an absolute path instead. This checks every retained run's marker, signature, inventory and all ciphertext bytes, and checks inventory again. No audit job or schedule is enabled. Investigate any failure and preserve all evidence.

Publication is split into isolated phases so no single compromised dependency sees every secret: the dump step receives only `BACKUP_DATABASE_URL`, validates it with `check_db_url.py` and passes it to `pg_dump` explicitly via `--dbname`; the encryption/signing step receives only the signing private key (plus the public key) and uses a dedicated GNUPGHOME whose agent is killed and directory removed; the publisher step receives only the HMAC key and S3 credentials, imports only the public keys into a separate verification GNUPGHOME, and runs the AWS CLI with an explicit environment allowlist that excludes the database URL, HMAC key and signing material. `pg_dump`, GPG and the AWS CLI are each invoked with minimal environments. The pinned awscli 1.36.40 cannot build its argument parsers on Python 3.14 ("badly formed help string"), so the loopback CLI test runs under Python 3.12; the test is hermetic (isolated config/credentials, `AWS_EC2_METADATA_DISABLED`, path-style addressing, hostile proxy/profile/session variables removed, explicit readiness wait) and rejects unsupported interpreters with an actionable message.

Set `BACKUP_RECIPIENT_FINGERPRINT`, `BACKUP_PUBLIC_KEY`, `BACKUP_SIGNER_FINGERPRINT` and `BACKUP_SIGNING_PUBLIC_KEY` as environment variables after independent fingerprint verification. `BACKUP_PUBLIC_KEY` is the armored **encryption** public key; `BACKUP_SIGNING_PUBLIC_KEY` is the armored **signing** public key. Importing only the encryption key is not enough: the publisher and any restore or audit verify the manifest signature against the signing key, so signature verification fails closed before upload when the signing public key is absent. One-time operator setup after verifying fingerprints out of band: `gh variable set BACKUP_SIGNING_PUBLIC_KEY --env backup-production --body "$(cat signing-public.asc)"` (and the equivalent for `BACKUP_PUBLIC_KEY`); the stored fingerprints must match the imported keys. Store `BACKUP_DATABASE_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, and a randomly generated at least 32-byte hex `BACKUP_HMAC_KEY_HEX` as environment secrets. The HMAC key must remain stable and be backed up securely: rotation makes old runs unrecognized and blocks publication. It authenticates completion metadata only, not the archive's restore source. Never put the private decryption key in CI. The database URL and S3 credentials may have broad privileges; approve and limit them independently. The workflow pins AWS CLI 1.36.40, isolates its config with path-style addressing and disables retries; dependencies are not hash-pinned and require supply-chain review. A loopback S3 protocol fixture exercises the actual CLI paths, pagination and failure handling (`BACKUP_CLI_TEST=1` with that version installed); this does not prove B2 compatibility. Hosted Supabase currently runs PostgreSQL 17.6; the workflow installs the PGDG PostgreSQL 17 client, checks that `/usr/lib/postgresql/17/bin/pg_dump` exists and is executable, prints and verifies its major version, and then invokes that absolute binary for the dump. The same directory is prepended to `PATH` for later steps because the `pg_dump` resolved from `PATH` on `ubuntu-latest` is not guaranteed to be the installed 17 client. Recheck the hosted version and client compatibility periodically. Experimental retrieval downloads and checks every part, HMAC and independently trusted signing fingerprint before producing a local archive: `python3 scripts/backup/publish.py retrieve RUN_ID /secure/scratch/retrieved`; then use `archive.py unpack` as below. Retrieval cannot establish freshness or prove that final publication checks completed. No hosted restore is provided.

### Manual recovery runbook

There is no automated restore of a hosted instance. When an operator must recover:

1. Freeze writes: pause the workflow (`BACKUP_ENABLED=false` or disable it), stop every other bucket writer, and capture a fresh inventory of keys/sizes before touching anything. Record the inventory and current time in the incident log.
2. Preserve evidence: copy the signing public key, HMAC key and the exact candidate run IDs to a protected location; never paste keys or tokens into logs or issues. Keep all candidate objects until recovery succeeds.
3. Authenticate each candidate offline with `publish.retrieve RUN_ID /secure/scratch/retrieved`. This verifies the marker HMAC, signed v3 run ID/creation time, manifest signature against the independently trusted fingerprint, exact inventory and every ciphertext byte before writing one output directory. Treat failure as data loss for that candidate, not as a reason to skip verification.
4. Run `archive.py unpack` on the retrieved directory with the trusted signing fingerprint and the offline private decryption key. For a protected key, set `BACKUP_GPG_PASSPHRASE_FILE` to a regular, current-user-owned mode-0600 file containing its passphrase (no symlinks in the path); keep it on secure scratch and remove it after use. Never put the passphrase in an argument or log. Then inspect the SQL dump on a disposable host. Confirm the dump reflects the intended restore point; the marker time is creator-asserted, not a provider timestamp.
5. Restore the database only into a **new** Supabase project, never over the only copy:
   1. Create a fresh project in the same region and with the same Postgres/Auth major versions as the backup source. Do not reuse the damaged project.
   2. Apply this repository's migrations to recreate schema, roles, policies and Storage bucket metadata. For a linked hosted project use `supabase link --project-ref <ref>` then `supabase db push`; for a local disposable project use `supabase db reset --local --no-seed`. The Storage bucket migration is required before the load; object bytes are still absent.
   3. Load the unpacked data-only dump with a PostgreSQL 17 client, as a role allowed to write both schemas, using `psql "$TARGET_DATABASE_URL" -X -v ON_ERROR_STOP=1 -f verified.sql`. The dump contains only `COPY`/`INSERT` data for `public` and `auth`: it does not emit `CREATE SCHEMA`, roles, policies or extension DDL, so it must target an already migrated project. It deliberately omits `auth.schema_migrations`, which belongs to the provider's Auth version and would conflict with the target's history.
   4. Auth rows are included for referential integrity (`public.profiles` references `auth.users`). Validate login, password reset and session issuance for sampled users. Supabase Auth internals change between releases; if the source and target Auth versions differ, stop and use a version-matched project or an approved Auth migration rather than forcing data into incompatible tables.
   5. Recreate Storage buckets from the existing bucket migration and verify bucket visibility/limits. Uploaded covers, avatars, PDFs, audio, GIFs and image sequences are **not restored**; this data-only backup cannot recover object bytes.
   6. Compare per-table row counts and content hashes against the source evidence before any production step. Applying to production requires a separate approved plan with explicit operator authorization.
6. Only after a verified replacement is safely stored may an authorized operator remove obsolete runs. Use a reviewed exact-key list; never wildcard or delete objects whose ownership, completeness or authenticity is unknown. If any step disagreed with the recorded inventory, stop and escalate rather than pruning.

### Ambiguous runs and manual cleanup

Never assume a marker proves a completed run. Stop all writers and preserve the bucket; capture inventory and retain the signing and HMAC keys. An authorized operator must independently retrieve and verify candidate archives, assess freshness from trusted external evidence, and preserve adequate separately verified copies before considering any cleanup. Inventory unknown objects and incomplete multipart uploads separately; do not delete unowned data or assume these listings are complete. Manual deletion requires a reviewed, explicitly authorized per-object plan and independent verification of the exact targets. There is no validated general deletion procedure and no automated cleanup outside the attested stateless prune; if evidence or ownership is uncertain, stop and escalate. Stateless retention cannot detect a wholesale rollback to an older authentic state; that residual risk is accepted only by the explicit no-rollback attestation.

## Offline archive format and verification

For experiments only, generate an encryption-capable GPG key on a trusted machine; keep the private key offline, encrypted and backed up in a separately secured location with a tested recovery custodian. Export only the verified public key to the packaging environment. Verify its full fingerprint out of band. Losing the private key makes the archive unrecoverable. Never upload private keys, dumps, passwords or GPG home directories as CI artifacts, logs or repository files. The prototype does not generate database dumps and does not protect plaintext on disk: use an encrypted private scratch directory, `umask 077`, sufficient space and independently managed cleanup. Secure deletion on SSDs or hosted runners cannot be assumed.

```bash
umask 077
python3 scripts/backup/archive.py pack /secure/scratch/dump.sql /secure/scratch/archive --recipient ENCRYPTION_FINGERPRINT --signer SIGNING_FINGERPRINT
BACKUP_GPG_PASSPHRASE_FILE=/secure/scratch/passphrase python3 scripts/backup/archive.py unpack /secure/scratch/archive /secure/scratch/verified.sql --signer SIGNING_FINGERPRINT
```

This prototype requires Linux with `/proc` and `renameat2`. Encryption ignores GPG configuration and disables configured extra recipients; the specified encryption fingerprint is the only intended recipient. Version 2 signs the exact manifest with a separate signing key and verifies it against the independently trusted full primary signing fingerprint before reading ciphertext or decrypting. Version 1 unsigned archives are rejected. A signature authenticates the signer, not freshness: replay and compromised signing keys remain risks. Limits are enforced on actual source, compressed, ciphertext and decompressed bytes (600 MB each); parts are at most 40 MB. Linux directory descriptors, no-follow opens and atomic no-replace publication prevent pathname substitution and overwrite. Parent directories must exist and be trusted against untrusted writers. Scratch directories are private, but crashes or SIGKILL can leave plaintext behind: use encrypted scratch and arrange operator cleanup; secure deletion is not guaranteed.

Generate a distinct signing key. Protect its private key in a reviewed, restricted CI environment with approved access and rotation, never PR jobs. The packer needs the encryption public key, the signing public key and the signing private key; the restore environment holds the encryption private key and the independently verified signing public key. `BACKUP_PUBLIC_KEY` must contain the encryption public key and `BACKUP_SIGNING_PUBLIC_KEY` the signing public key; neither may contain private material. Restore and verification fail without the signing public key. `BACKUP_SIGNING_PRIVATE_KEY` is the separate unprotected signing private key, stored as a protected environment secret; the workflow does not supply a signing passphrase. Pin `BACKUP_SIGNER_FINGERPRINT` independently and review the risks of an unprotected CI signing key.

## Disposable restore verification

```bash
BACKUP_DOCKER_TEST=1 python3 -m unittest discover -s scripts/backup -v
```

This creates a fresh Docker `postgres:16` container without network access or published ports, creates a fixture database, dumps it, packages and unpacks it, restores into a second fresh database in that container, verifies a row and removes the container. It cannot restore to a supplied URL or live database. Docker image availability and daemon access are required. This tests only a generic PostgreSQL fixture, not hosted Supabase, Auth, permissions, extensions or Storage.

The backup contract drill exercises the actual data-only dump and a freshly migrated Supabase schema:

```bash
scripts/backup/restore_drill.sh \
  'postgresql://postgres:postgres@127.0.0.1:54322/postgres' \
  'postgresql://postgres:postgres@127.0.0.1:55322/postgres'
```

The script accepts only loopback hosts, refuses the same database as source and target, and never prints URLs or secrets. It verifies the target is freshly migrated with no application rows, dumps `public` and `auth` data-only (excluding `auth.schema_migrations`), packs and signs an ephemeral archive, unpacks it with a passphrase file, restores with `ON_ERROR_STOP=1`, and compares per-table row counts and content hashes. To produce an isolated target, use a second local Supabase project with a unique `project_id` and non-overlapping ports, run `supabase db start` and then `supabase db reset --local --no-seed` for that project. The drill proves local schema/data restore only: it does not prove hosted Supabase Auth version compatibility, role differences or object-byte recovery. No live restore command is provided; recovering a hosted instance requires a separately reviewed plan and explicit operator approval. Do not point generic SQL restore at production.
