# Backup and recovery: offline prototype, activation blocked

**The publication workflow is hard-disabled and is not production-ready.** The repository contains a scheduled and manually dispatched workflow and a remote publisher, but the job cannot run until its hard-disable is deliberately removed after review. No provider or credentials were accessed during validation. Archives use signed version 2 manifests and bounded streams. Integration remains experimental and independent review is mandatory before activation. The publisher's HMAC authenticates metadata, not proof that a previous run completed its final readback and inventory.

## Activation blockers

Before implementing/activating a weekly workflow, the operator and security reviewer must approve all of the following:

1. An actual shared-Storage budget and reservation strategy. The 1 GB Free allocation is shared with public/private assets and backups; the 500 MB database limit does not imply three encrypted dumps plus a fourth in progress fit. Retention cannot free previous copies *before* a verified replacement. Provider quota/account usage and incomplete uploads must be accounted for safely. Fail closed and alert when no headroom; no paid/card fallback is approved.
2. DB dump scope, consistency and hosted restore strategy: Supabase-managed Auth, Storage metadata, extensions, roles, migration history and provider-managed schemas require separate review. A generic `pg_dump` is not evidence that hosted Supabase is recoverable. Test the precise approved dump and restore procedure against a disposable Supabase project before relying on it.
3. Scoped server-side Storage and database credentials, their ownership, rotation and incident response; demonstrate that the selected API supports bounded listing, upload, read-back and deletion without exposing credentials. Supabase S3 credentials may be broad: review effective permissions rather than assuming bucket scoping. Never put them in app code or PR jobs. Select an operator-approved key custodian and offline recovery process.
4. Independently review and test the publisher and signed archive integration. The intended weekly newest-three retention is **not implemented**; automatic deletion is disabled. Version 2 has no authenticated creation time: never order it by Storage timestamps or random run IDs. A future protocol needs authenticated immutable time/run identity, trusted clock and uniqueness/skew policy, exclusive writer, and a trusted out-of-band high-water mark (or explicit acceptance that wholesale rollback is undetectable). It must reverify three survivors including the new run before any exact-key deletion; never fund an upload by deleting first. Until then retain all runs, fail on the cap, and use only separately approved manual rotation. GitHub concurrency only serializes this workflow; it cannot lock out external writers. Operators must enforce exclusive access independently. Unknown or incomplete objects block publication; an inventory comparison detects some overlaps but not same-size overwrites or changes between checks.
5. A protected GitHub environment with required reviewers, no self-approval where supported, and branch restriction to protected main; confirm the repository plan actually enforces those settings before storing secrets. A YAML environment name alone is not protection. Agree how weekly schedules interact with required approvals, alerting and operator absence; do not disable approval to make cron work. Scheduling and any first backup need separate authorization.

Until these decisions and an independently reviewed/tested implementation exist, **do not enable the workflow, provision backup credentials, upload a production dump, or prune the bucket**. The intended destination remains the existing private `educador-backups` bucket, not a new service. Its object cap is 50 MB; provider quota values must be rechecked. Uploaded covers, avatars, PDFs, audio, GIFs and image sequences are separate object bytes: a DB dump only contains metadata/references. YouTube videos remain on YouTube. No object backup, object recovery, or offsite disaster protection exists here. The backup bucket is in the same provider/project, so it is not an independent disaster-recovery location.

## Publisher configuration and limitations

The disabled workflow uses the `backup-production` environment; configure required reviewers, prevent self-approval where supported, restrict deployment to protected `main`, and verify actual plan enforcement. GitHub scheduled jobs may wait for approval, and concurrency may replace pending runs; monitor failures and missed runs. `BACKUP_ENABLED` must be the repository variable `true`, and manual runs also require the confirmation input. Removing the hard-disable requires a reviewed code change after all blockers are resolved.

Environment variables: `BACKUP_S3_ENDPOINT` is the exact HTTPS Supabase Storage S3 endpoint; `BACKUP_TOTAL_BUDGET_BYTES` is an operator-approved allocation no greater than 1,000,000,000 bytes. `BACKUP_NON_BACKUP_RESERVE_BYTES` must cover all other project storage, growth and **all incomplete multipart uploads**, including uploads outside this bucket. `ListObjectsV2` does not include multipart parts. This code does not inventory multipart uploads and cannot automatically establish headroom; a conservative independently verified reserve and prohibition of other multipart writers are mandatory. `BACKUP_EXCLUSIVE_WRITER_ATTESTED` and `BACKUP_MULTIPART_RESERVE_ATTESTED` must both be `true`, but are operator assertions, not technical locks or proof. Unknown/incomplete listed objects fail closed. Ensure the bucket exists, is private, and accepts `application/octet-stream` objects up to 40,000,000 bytes. Monitor actual usage and update the reserve; concurrent growth beyond it invalidates the estimate.

`BACKUP_EGRESS_BUDGET_BYTES` must cover the new archive readback, every byte of all prior objects up to the remaining storage allocation, and a 10 MB listing/protocol allowance; this conservative estimate is checked before S3 requests. Each existing marker is only a candidate: its HMAC, signed manifest, exact inventory and all current ciphertext bytes must independently verify before another run can proceed. This also permits a complete authentic candidate left by interruption after marker PUT; it does not prove historical readback or hosted restorability. Missing, incomplete, unknown or tampered objects block publication. Full revalidation can cost about 2.4 GB for four 600 MB archives, if storage permits. Reserve a conservative monthly project-wide allowance as well as the per-run estimate. The allowance is not a hard network cap: an adversarial server, unbounded list pages, protocol errors, or unexpected SDK behavior can exceed it. CLI output and downloaded file sizes are locally bounded, but this does not bound provider traffic; provider-side traffic limits and isolated testing remain activation blockers.

Set `BACKUP_RECIPIENT_FINGERPRINT` and `BACKUP_PUBLIC_KEY` as environment variables after independent fingerprint verification. Store `BACKUP_DATABASE_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, and a randomly generated at least 32-byte hex `BACKUP_HMAC_KEY_HEX` as environment secrets. The HMAC key must remain stable and be backed up securely: rotation makes old runs unrecognized and blocks publication. It authenticates completion metadata only, not the archive's restore source. Never put the private decryption key in CI. The database URL and S3 credentials may have broad privileges; approve and limit them independently. The workflow pins AWS CLI 1.36.40, isolates its config with path-style addressing and disables retries; dependencies are not hash-pinned and require supply-chain review. A loopback S3 protocol fixture exercises the actual CLI paths, pagination and failure handling (`BACKUP_CLI_TEST=1` with that version installed); this does not prove Supabase compatibility. GPG and compatible `pg_dump` must be checked against the hosted PostgreSQL version. Experimental retrieval downloads and checks every part, HMAC and independently trusted signing fingerprint before producing a local archive: `python3 scripts/backup/publish.py retrieve RUN_ID /secure/scratch/retrieved`; then use `archive.py unpack` as below. Retrieval cannot establish freshness or prove that final publication checks completed. No hosted restore is provided.

### Ambiguous runs and manual cleanup

Never assume a marker proves a completed run. Stop all writers and preserve the bucket; capture inventory and retain the signing and HMAC keys. An authorized operator must independently retrieve and verify candidate archives, assess freshness from trusted external evidence, and preserve adequate separately verified copies before considering any cleanup. Inventory unknown objects and incomplete multipart uploads separately; do not delete unowned data or assume these listings are complete. Manual deletion requires a reviewed, explicitly authorized per-object plan and independent verification of the exact targets. There is no automated cleanup or validated general deletion procedure; if evidence or ownership is uncertain, stop and escalate. No safe three-newest retention exists without a replay-resistant external ordering/commit proof.

## Offline archive format and verification

For experiments only, generate an encryption-capable GPG key on a trusted machine; keep the private key offline, encrypted and backed up in a separately secured location with a tested recovery custodian. Export only the verified public key to the packaging environment. Verify its full fingerprint out of band. Losing the private key makes the archive unrecoverable. Never upload private keys, dumps, passwords or GPG home directories as CI artifacts, logs or repository files. The prototype does not generate database dumps and does not protect plaintext on disk: use an encrypted private scratch directory, `umask 077`, sufficient space and independently managed cleanup. Secure deletion on SSDs or hosted runners cannot be assumed.

```bash
umask 077
python3 scripts/backup/archive.py pack /secure/scratch/dump.sql /secure/scratch/archive --recipient ENCRYPTION_FINGERPRINT --signer SIGNING_FINGERPRINT
python3 scripts/backup/archive.py unpack /secure/scratch/archive /secure/scratch/verified.sql --signer SIGNING_FINGERPRINT
```

This prototype requires Linux with `/proc` and `renameat2`. Encryption ignores GPG configuration and disables configured extra recipients; the specified encryption fingerprint is the only intended recipient. Version 2 signs the exact manifest with a separate signing key and verifies it against the independently trusted full primary signing fingerprint before reading ciphertext or decrypting. Version 1 unsigned archives are rejected. A signature authenticates the signer, not freshness: replay and compromised signing keys remain risks. Limits are enforced on actual source, compressed, ciphertext and decompressed bytes (600 MB each); parts are at most 40 MB. Linux directory descriptors, no-follow opens and atomic no-replace publication prevent pathname substitution and overwrite. Parent directories must exist and be trusted against untrusted writers. Scratch directories are private, but crashes or SIGKILL can leave plaintext behind: use encrypted scratch and arrange operator cleanup; secure deletion is not guaranteed.

Generate a distinct signing key. Protect its private key and passphrase in a reviewed, restricted CI environment with approved access and rotation, never PR jobs; use an agent or protected file descriptor for passphrases, never command-line arguments or logs. The packer only needs the encryption public key, while the restore environment holds the encryption private key and independently verified signing public key. The disabled workflow imports `BACKUP_SIGNING_PRIVATE_KEY` from a protected environment secret and pins `BACKUP_SIGNER_FINGERPRINT` independently; it does not supply a passphrase and therefore requires a separately reviewed noninteractive key-unlocking design before use. This integration is not approved for production.

## Disposable restore verification

```bash
BACKUP_DOCKER_TEST=1 python3 -m unittest discover -s scripts/backup -v
```

This creates a fresh Docker `postgres:16` container without network access or published ports, creates a fixture database, dumps it, packages and unpacks it, restores into a second fresh database in that container, verifies a row and removes the container. It cannot restore to a supplied URL or live database. Docker image availability and daemon access are required. This tests only a generic PostgreSQL fixture, not hosted Supabase, Auth, permissions, extensions or Storage. No live restore command is provided: recovering a hosted instance requires a separately reviewed plan and explicit operator approval. Do not point generic SQL restore at production.
